# Future Workbench v1

From `D:\Future`, run **`python -m workbench`**, then open **http://127.0.0.1:8000**. If that port is occupied, use `python -m workbench --port 8766`. Initial setup needs Node/npm, the root Python requirements, and network access for the pinned frontend/backend packages. Subsequent launches and engine execution work offline. Use `--no-build` to reuse an existing frontend build. Stop with Ctrl+C.

The app is a localhost research tool around the unchanged 54 Core v1 engines and Future Lab. It adds no inference models, cloud services or authentication. It does not certify empirical validity. The API and built UI share one loopback server. For frontend development run the backend and `npm run dev` inside `workbench/web`; Vite forwards `/api` to localhost:8000.

## Using the application

1. **Explore:** Search 54 retained methods, select one, inspect the pinned capability/release/source records. Six inventory phases and six excluded IDs follow the original inventory.
2. **Studio:** Load the verified sample, edit human fields, validate and run. Birth/location/CLI operations have explicit native argument descriptors; nested native requests have typed fields and repeatable lists. Samples are starting documents, not full schemas. Optional conventions absent from a sample can be entered in Advanced JSON; native validation remains authoritative. Switching legacy operations resets their required inputs rather than reusing unrelated positional values. Profile/hash fields are pinned in the regular editor. Changed provenance/ledger commitments may require a correctly rebuilt native request in advanced mode. Validation executes the actual engine and can be as expensive as a run.
3. **Cases:** Create a pseudonymous participant with explicit permitted scopes and technique IDs, then a case. Select that case in Studio's session context. Nicknames are optional. Notes and native inputs/results are stored locally. Sample runs carry a sample label and count separately; editing a sample changes the input origin to manual, which still does not certify that it is an actual observation.
4. **Blind:** An assessor enters a separate hidden answer during setup, then runs the engine and hands the tester the screen. The answer input is cleared and the API withholds its stored value. The native request itself must omit answers; the app cannot remove semantic leakage from arbitrary native inputs or results. Record an immutable interpretation, lock, then reveal. Optional alternatives receive shuffled stable labels. Assessor identity/ratings are declarations; 1–5 agreement is descriptive, never a universal accuracy score. Imported unrevealed sessions cannot reveal an answer because portable exports deliberately omit secrets.
5. **Prospective:** Use the #51 binary-event form with explicit future cutoff/window, positive/negative rules, independent resolution source, probability, reasoning and self-authored evidence. The server stamps issuance now. A fixed 1/2 baseline is committed. No known outcome is prefilled. After the complete observation window, an assessor records independent evidence, known time and outcome; Future Lab enforces chronology and computes exact matched scores. Missing/excluded records remain unscored. Advanced native Lab plans for #49/#51/#57 retain all admission guards; outer creation/selection times and forecast issuance are stamped now. Native availability, identities, commitment hashes and future target times must already be valid.
6. **Compare:** Select runs for descriptive side-by-side inputs, outputs and provenance. Quantitative comparison is delegated to Lab and rejects incompatible contracts, events, datasets, outcomes or cutoffs. Independently created events are deliberately not silently matched.
7. **Research:** Counts come from actual local records; samples remain visible. Filters select technique, study label, participant ID and ISO time range. Per-study reports expose matched losses, baseline, coverage and calibration; no fabricated aggregate accuracy or confidence interval. JSON exports include full public records plus integrity hashes, CSV/Markdown provide summaries. Import checks commitments and rejects conflicting IDs; repeating the same export adds no duplicates.

## Storage, consent and deletion

SQLite schema migration 1 is explicit in `store.py`. Transactions serialize writes; clients send idempotency keys. Identical key/payload retries return the existing record; conflicting payloads fail. Data defaults to `%USERPROFILE%\.future-workbench\workbench.sqlite3`, outside the repository. Override `FUTURE_WORKBENCH_HOME` for an isolated workspace. SQLite is **not encrypted**. Use an account/disk protection appropriate to the inputs. Back up the whole directory while the app is stopped.

Participant/case deletion previews affected counts. Without separate retention consent it deletes active cases, linked sessions, studies and secrets. Separate frozen-retention consent allows already-locked sessions/studies to become detached archives; these intentionally retain original inputs and may contain sensitive details. This retention is explicit, not anonymization. Downloaded exports, backups and operating-system remnants are outside the deletion operation. A local machine/DB owner can read secrets: this is workflow blinding, not protection against the database administrator. No third-party requests, image uploads, external source fetching or arbitrary kernel-file access are provided.

Unlinked exploration runs and researcher forecasts can be deleted from Cases → Unlinked local runs & forecasts, or from the current unlinked Studio result. They have no participant retention consent and are removed directly. Linked runs follow the owning case/participant deletion policy.

## Supported boundaries and backlog

- Supported: all 54 sample invocation paths; native operation selection; recursive fields and raw JSON; native errors/provenance; local consent/cases; blind lock/reveal; prospective #51 form; guarded advanced Lab plans for #49/#57; immutable outcome scoring; descriptive/eligible comparison; filters; import/export; active deletion and separately consented frozen retention.
- **Versioned corrections are annotations only.** Void/disputed/correction dispositions are append-only, suspend scoring and preserve the original Lab ledger/report for inspection. They never overwrite a numeric outcome or falsely claim a corrected score. Historical numeric replacement requires a later legitimate native protocol/version and is deferred. New future studies can be created; past forecasts cannot be backdated. The app does not provide an external timestamp authority.
- Advanced #49/#57 plans require native protocol expertise; bespoke prospective forms for them are P1. Full schema coverage beyond verified sample fields and commitment-aware native ledger builders are P1. Native unknown/unsupported states are preserved and may require reading the structured output.
- P1: per-target disposition retraction/adjudication with a new explicit version; richer case/session follow-up editing with version history; archive selection/deletion UI; better controlled vocabulary and field help per native variation.
- P2: encrypted-at-rest workspace integration; independently authenticated commitments; multi-assessor access isolation; additional accessible result tables. No multi-user/server deployment is claimed.

## Verification

- Backend: `python -m unittest discover -s workbench/tests -v` (separate from the frozen inherited suite).
- Install backend test dependencies with `python -m pip install -r workbench/test-requirements.txt` when needed. The measured Workbench checks can be rerun with `python -m workbench.accept`; `--finalize` verifies unchanged measured source hashes and incorporates a completed inherited receipt without rerunning tests.
- Frontend: `cd workbench/web`, `npm ci`, `npm run build`, `npx playwright install chromium`, `npm run test:e2e`.
- Browser tests use a temporary database and a clearly synthetic controllable clock on port 8765. That clock route exists only in `workbench.e2e_server`, never `python -m workbench`.
- Full inherited suite: `python -m workbench.accept_inherited`; writes a new Workbench receipt and compares byte hashes of pre-existing tracked files, excluding README/PROGRESS/.gitignore integration edits. Do not run old acceptance writers to incorporate new Workbench results into frozen Lab receipts.

For portable record integrity, keep the JSON file's original numeric representations. The UI downloads/uploads original server JSON text; parsing and rewriting it in another tool can change native commitments (for example, `1.0` to `1`). Newly imported native sessions are independently replayed before admission. Imports are bounded to 8 MiB; use participant exports to keep a large workspace portable.

See `inherited-acceptance.json`, `browser-acceptance.json` and the final `acceptance.json` for measured results. A passing software test is not empirical validation of the methods.
